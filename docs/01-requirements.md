## 1. 项目定位

RDVP 是一个基于 HarmonyOS 的远程设备档案查询与运维协同系统，面向分布式设备的现场查询、状态核验、档案增删改申请、故障报修、维修处理和审计追踪等业务场景。

系统由 HarmonyOS 移动端应用和后端服务共同组成。移动端负责现场操作入口、数据采集和业务交互；后端服务负责身份认证、权限控制、设备数据管理、业务流程流转、数据校验、审核和审计记录。消息推送、附件存储和离线同步为后续增强能力。

## 2. 业务目标

RDVP 的核心目标如下：

- 支持用户通过设备编号或二维码远程查询设备档案。
- 支持现场人员对设备状态进行核验并形成核验记录。
- 支持设备档案添加、删除和修改申请，由管理员审核后生效。
- 支持设备故障报修和故障状态跟踪。
- 支持将维修任务和复检任务推荐给一定范围内且符合负载条件的人员，提高响应效率。
- 支持维修人员自主接取维修任务并填写维修任务报告。
- 支持根据故障等级决定维修后是否必须复检，并由复检人员填写复检任务报告。
- 支持在线提交为准的业务闭环；离线草稿和恢复网络后同步为后续增强能力。
- 支持完整日志查询和业务审计，保证关键业务可追溯。

## 3. 系统边界

### 3.1 移动端应用

HarmonyOS 移动端应用主要提供以下能力：

- 用户登录和退出登录。
- 设备档案查询，包含设备编号查询和二维码查询。
- 设备档案详情查看。
- 设备档案添加、删除和修改申请。
- 设备状态核验。
- 设备故障报修。
- 维修和复检任务查看与接取。
- 维修任务报告填写。
- 复检任务报告填写。
- 档案审核，包含添加档案、删除档案、修改档案操作。
- 运维审核，包含核验报告、报修报告、维修报告和复检报告操作。
- 日志查询档案、运维和审核日志。

### 3.2 后端服务

后端服务主要提供以下能力：

- 用户认证。
- 角色和权限控制。
- 设备档案管理。
- 设备二维码防伪校验。
- 设备档案添加、删除和修改审核。
- 设备故障报修管理。
- 维修和复检任务推荐。
- 维修任务接取和状态流转。
- 维修任务报告管理。
- 复检任务报告管理。
- 日志查询和审计查询。

### 3.3 数据存储

系统至少需要存储以下业务数据：

- 用户和角色数据。
- 设备基础数据。
- 设备状态核验记录。
- 设备档案添加、删除和修改申请。
- 设备故障报修。
- 维修任务。
- 维修任务报告。
- 复检任务报告。
- 记录和审计日志。

## 5. 核心业务流程

### 5.1 用户登录流程

1. 用户打开移动端应用。
2. 移动端检查本地访问凭证是否存在且未过期。
3. 凭证有效时，移动端直接进入主界面。
4. 凭证不存在或已过期时，移动端进入登录界面。
5. 用户输入账号和密码。
6. 移动端将登录请求提交至后端服务。
7. 后端校验用户身份、账号状态和权限范围。
8. 后端返回访问凭证、用户信息和权限信息。
9. 移动端保存凭证并根据用户权限展示可用功能。

业务结果：系统确认当前用户身份，并明确用户可以执行的业务操作。

默认本地凭证有效期为 7 天。用户主动退出登录或凭证过期后，移动端必须清理本地会话并重新进入登录界面。

### 5.2 设备编号查询流程

1. 用户进入设备档案查询功能。
2. 用户输入设备编号。
3. 移动端提交设备编号至后端服务。
4. 后端校验设备编号格式和设备存在性。
5. 后端返回设备基础信息、当前状态、最近核验记录、故障记录和维修记录摘要。
6. 移动端进入设备档案详情页面，展示设备档案和状态信息。

业务结果：用户通过设备编号确认设备真实信息和当前运维状态。

### 5.3 二维码查询流程

1. 用户进入设备档案查询功能，并选择二维码查询。
2. 用户扫描设备二维码，或上传包含设备二维码的图片。
3. 移动端解析二维码内容，并提交至后端服务。
4. 后端校验二维码版本、设备编号、随机标识和防伪签名。
5. 校验通过后，后端返回设备档案和状态信息。
6. 校验失败时，移动端提示二维码无效或设备身份存疑。

业务结果：用户通过带防伪校验的二维码查询设备，降低设备伪造和二维码伪造风险。

二维码不应直接保存敏感设备详情。推荐二维码内容包含：

- 二维码版本号。
- 设备编号。
- 随机标识。
- 防伪签名或校验码。

### 5.4 设备状态核验流程

1. 现场运维人员进入设备详情。
2. 现场运维人员检查设备现场状态。
3. 现场运维人员填写核验结果、现场描述和备注。
4. 后续附件能力落地后，现场运维人员可按需上传现场照片或附件。
5. 移动端提交核验记录至后端服务。
6. 后端保存核验记录，更新设备最近核验时间。
7. 后端写入操作日志。

业务结果：系统形成一次可追溯的设备状态核验记录。

### 5.5 设备档案添加/删除/修改申请流程

1. 用户在设备档案详情中发现设备信息缺失、错误、已过期，或者决定新增、删除档案。
2. 用户从设备档案详情进入对应的档案申请页面。
3. 移动端预填当前设备档案信息或目标档案信息。
4. 用户补充需要提交的新增内容、删除原因或修改字段，并填写申请原因。
5. 移动端提交设备档案申请。
6. 后端校验当前设备是否存在待审核申请或处于申请冻结期。
7. 后端保存申请内容，记录申请前后的差异或目标档案信息，并将申请状态置为待审核。
8. 设备管理员查看待审核申请。
9. 设备管理员选择审核通过或审核驳回。
10. 审核通过后，后端正式创建、更新或删除档案。
11. 审核结束后（通过或驳回），后端从审核完成时间开始设置 6 小时申请冻结期。
12. 审核驳回时，后端记录驳回原因并解除待审核锁定。
13. 后端写入操作日志。

业务结果：设备档案的新增、删除和修改必须经过管理员审核，避免误改、恶意修改和无痕修改。

约束：

- 同一设备同一时间只能存在一个待审核档案申请。
- 设备存在待审核申请时，移动端应禁用再次提交入口，后端必须拒绝新的申请。
- 申请审核结束后（通过或驳回），后端应对该设备或目标设备编号设置 6 小时申请冻结期，冻结期从审核完成时间开始计算。
- 用户从设备档案详情进入档案申请后，未提交前返回详情页时应保留本次草稿；离开设备档案详情流程后草稿应清空。

### 5.6 设备故障报修流程

1. 用户查询到目标设备。
2. 用户进入设备故障报修功能。
3. 用户填写故障类型、故障描述、故障等级、发生时间和现场情况。
4. 后续附件能力落地后，用户可按需上传现场照片或附件。
5. 移动端提交设备故障报修至后端服务。
6. 后端生成设备故障报修编号。
7. 后端将故障状态置为待接取。
8. 后端按业务规则更新设备状态。
9. 后端写入操作日志。

业务结果：设备故障被正式登记，并进入维修响应流程。

### 5.7 维修任务推荐与接取流程

1. 新设备故障报修创建后，后端根据设备位置计算推荐范围。
2. 系统默认可先使用 10km 作为附近维修人员推荐半径。
3. 后端根据维修人员当前进行中的维修任务数判定负载状态，并据此限制可接取范围和接取资格。
4. 维修人员刷新可接取任务列表并查看符合条件的故障任务。
5. 维修人员查看故障详情。
6. 维修人员可自主选择是否接取该故障。
7. 若维修人员接取成功，后端创建维修任务并更新故障状态。
8. 若多个维修人员同时接取，后端只允许最先成功接取的人员获得任务。

维修人员负载规则：

- 无进行中维修任务时判定为空闲，可查看和接取全范围内的可接取故障。
- 有进行中维修任务但未达到上限时判定为低负载，仅可查看和接取较小范围内的可接取故障。
- 进行中维修任务达到上限时判定为忙碌，暂不可刷新任务池或接取额外任务。

业务结果：系统将故障快速暴露给附近可响应的维修人员，同时保留维修人员自主接取机制。

### 5.8 维修任务报告流程

1. 维修人员查看已接取的维修任务。
2. 维修人员到达现场并处理故障。
3. 维修人员填写维修过程、维修结果、更换部件、维修时间和备注。
4. 后续附件能力落地后，维修人员可按需上传维修前后照片或附件。
5. 移动端提交维修任务报告至后端服务。
6. 后端保存维修任务报告。
7. 后端根据故障等级判断是否需要复检。
8. 不需要复检时，故障可进入待关闭或已关闭状态。
9. 需要复检时，故障进入待复检状态。
10. 后端写入操作日志。

业务结果：维修行为被正式记录，故障状态按业务规则推进。

### 5.9 复检任务报告流程

1. 重大故障或被指定需要复检的故障，在维修完成后进入待复检状态。
2. 复检人员查看待复检任务。
3. 复检人员现场检查维修结果。
4. 复检人员填写复检结论和复检说明；后续附件能力落地后可补充附件。
5. 复检通过时，设备状态可恢复为正常或可用状态。
6. 复检不通过时，故障重新进入维修处理流程。
7. 后端写入操作日志。

业务结果：重大故障维修结果经过复检确认后才能关闭，保证设备恢复状态可信。

### 5.10 后续增强：离线填写与同步流程

1. 用户在无网络或弱网络状态下使用移动端应用。
2. 移动端主动提示当前处于非联网状态。
3. 用户可继续填写核验记录、设备故障报修、维修任务报告或设备档案申请草稿。
4. 移动端将数据保存为本地草稿或待同步记录。
5. 网络恢复后，移动端提示用户进行同步。
6. 移动端将待同步数据提交至后端服务。
7. 后端校验数据有效性、用户权限和业务状态。
8. 同步成功后，移动端更新本地记录状态。
9. 同步失败时，移动端保留失败原因并允许用户修改后重试。

业务结果：后续离线能力落地后，系统支持离线填写；正式业务生效仍必须以后端成功接收为准。

### 5.11 日志查询与审计流程

1. 用户进入日志查询。
2. 用户查看档案日志、运维日志和审核日志。
3. 主管或审计人员查看操作日志。
4. 系统支持按设备、人员、时间、状态等条件筛选记录。

业务结果：设备全生命周期记录可查询、可追溯、可审计。

## 6. 业务状态

### 6.1 设备状态

| 状态 | 说明 |
| --- | --- |
| 正常 | 设备当前可正常使用 |
| 待核验 | 设备需要现场核验 |
| 档案待审核 | 设备存在待审核的档案申请 |
| 故障中 | 设备存在已登记故障 |
| 维修中 | 设备故障已被维修人员接取并处理中 |
| 待复检 | 设备维修完成但需要复检确认 |
| 停用 | 设备暂时停止使用 |
| 报废 | 设备已退出使用 |

### 6.2 设备档案申请状态

| 状态 | 说明 |
| --- | --- |
| 待审核 | 档案申请已提交，等待管理员审核 |
| 审核通过 | 档案申请已通过，对应档案操作已生效 |
| 审核驳回 | 档案申请未通过，对应档案操作未生效 |
| 已撤回 | 申请人主动撤回档案申请 |

### 6.3 故障报告状态

| 状态 | 说明 |
| --- | --- |
| 已提交 | 设备故障报修已创建 |
| 待接取 | 故障等待维修人员接取 |
| 已接取 | 故障已被维修人员接取 |
| 维修中 | 维修人员正在处理故障 |
| 维修完成 | 维修人员已提交维修任务报告 |
| 待复检 | 故障维修完成后等待复检 |
| 已关闭 | 故障处理流程已结束 |
| 已驳回 | 设备故障报修被判定无效或不成立 |

### 6.4 维修任务状态

| 状态 | 说明 |
| --- | --- |
| 待接取 | 故障任务尚未被维修人员接取 |
| 已接取 | 维修人员已接取任务，需继续处理 |
| 维修中 | 维修人员正在处理任务 |
| 报告已提交 | 维修人员已提交维修任务报告，等待后续关闭或复检 |

### 6.5 后续增强：离线数据状态

| 状态 | 说明 |
| --- | --- |
| 本地草稿 | 数据只保存在移动端本地，尚未准备提交 |
| 待同步 | 数据已准备提交，但尚未同步到后端 |
| 同步中 | 数据正在提交至后端 |
| 同步失败 | 后端未成功接收，需用户处理后重试 |
| 已同步 | 数据已被后端成功接收 |

## 8. 安全要求

### 8.1 身份认证

- 用户必须登录后才能访问业务功能。
- 后端必须校验访问凭证有效性。
- 访问凭证应具备过期机制。
- 移动端不得明文保存用户密码。

### 8.2 权限控制

- 后端必须对每个关键接口进行权限校验。
- 移动端隐藏无权限功能只作为用户体验优化，不能替代后端权限校验。
- 设备档案申请、故障关闭、维修任务报告提交、复检任务报告提交等关键操作必须记录操作人。

### 8.3 二维码防伪

- 二维码不能只包含设备编号。
- 二维码内容必须具备防伪校验能力。
- 移动端扫码结果必须提交后端验证，不能在本地直接判定设备可信。
- 后端应支持二维码版本升级，避免后续算法升级时无法兼容。

### 8.4 数据完整性

- 后端必须校验设备编号、报告内容和状态流转；后续附件能力落地后还必须校验附件元数据。
- 关键状态流转不能仅依赖移动端传参。
- 设备档案修改申请必须保存修改前后差异。

### 8.5 后续增强：附件安全

- 上传附件必须限制文件类型和文件大小。
- 后端必须校验上传文件，不得只依赖文件扩展名。
- 附件访问必须进行权限控制。

### 8.6 记录和审计日志

以下操作必须写入审计日志：

- 用户登录和退出。
- 设备档案申请提交。
- 设备档案申请审核。
- 设备故障报修提交。
- 维修任务接取。
- 维修任务报告提交。
- 复检任务报告提交。
- 故障关闭。
- 权限和角色变更。

## 9. 非功能要求

### 9.1 可维护性

- 项目目录、文件命名、接口命名和数据库命名必须统一。
- 业务规则应集中定义，避免散落在多个页面或接口中。
- 文档应随需求和代码同步维护。

### 9.2 可扩展性

- 角色权限模型应支持新增角色。
- 设备状态和故障等级应支持配置或枚举扩展。
- 二维码校验方案应支持版本升级。
- 后端接口应预留分页、筛选和排序能力。

### 9.3 可追溯性

- 关键业务数据必须保留创建人、创建时间、更新人、更新时间。
- 关键状态流转必须保留业务记录。
- 审核、接取、维修、复检等业务动作必须可追溯。

### 9.4 时效性

- 新故障应能在维修人员刷新任务列表时及时进入可接取范围。
- 当前版本正式业务提交以在线后端响应为准。
- 后续消息推送和离线同步能力落地后，应补充推送时效和未同步数据提示要求。

## 10. 第一版建议范围

第一版建议优先实现以下能力：

- 用户登录。
- 基于角色的基础权限控制。
- 设备档案查询，包含设备编号查询和二维码查询。
- 二维码后端防伪校验。
- 设备档案详情展示。
- 设备档案添加、删除和修改申请以及管理员审核。
- 设备故障报修提交。
- 维修和复检任务推荐。
- 维修人员自主接取。
- 维修任务报告提交。
- 重大故障复检任务流程。
- 档案审核和运维审核。
- 日志查询。
- 操作日志记录。

以下能力可作为后续增强：

- 更复杂的派单策略。
- 地图可视化调度。
- 统计报表。
- 多组织和多租户管理。
- 消息中心。
- 附件上传和存储。
- 离线待同步内容和同步状态提示。
- 设备生命周期全量资产管理。
- 与外部系统集成。

## 11. 待确认问题

- 故障等级如何划分，以及每个等级对应的处理时限。
- 设备位置来源是固定档案、扫码现场定位，还是两者结合。
- 附件是否需要支持视频。
- 离线待同步内容是否需要加密存储。
- 管理员审核是否需要多级审批。
- 是否需要 Web 管理后台。
- 是否需要消息推送的已读、未读和超时提醒机制。
