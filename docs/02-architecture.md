## 1. 架构目标

RDVP 的架构设计目标如下：

- 支持 HarmonyOS 移动端完成现场档案查询、核验、故障报修、维修任务接取、维修任务报告和复检任务报告等业务。
- 支持后端统一管理设备数据、业务流程、权限控制、审核和日志。
- 保证关键业务状态以后端为准，移动端不能绕过后端直接改变设备真实状态。
- 当前版本采用在线提交优先架构，正式业务数据必须在后端校验通过后才生效；离线同步、附件和推送为后续增强能力。
- 支持后续扩展 Web 管理后台、统计报表、多组织管理和外部系统集成。

## 2. 总体架构

当前 RDVP 采用移动端、后端服务和数据库分层架构。文件存储、推送服务和离线同步服务为后续扩展。

## 3. 工程边界

### 3.1 HarmonyOS App

移动端应用负责用户交互和现场数据采集，不能承担最终业务判定职责。

主要职责：

- 展示用户可访问的功能入口。
- 采集设备编号、二维码、核验内容、故障内容、维修内容和审核内容。
- 管理页面态和必要的本地会话数据。
- 调用后端接口完成业务提交和查询。

移动端不得承担以下职责：

- 不得在本地直接判定二维码真实可信。
- 不得在本地直接改变设备最终状态。
- 不得在本地绕过权限控制。
- 不得保存明文密码、长期密钥或生产环境敏感配置。

### 3.2 Backend Service

后端服务是业务事实来源，负责所有关键业务规则和状态流转。

主要职责：

- 登录认证和访问凭证签发。
- 用户、角色和权限校验。
- 设备基础信息维护。
- 档案添加、删除和修改申请及审核。
- 二维码防伪校验。
- 设备故障报修创建和状态流转。
- 附近维修人员筛选和故障推荐。
- 维修任务接取并发控制。
- 维修报告保存和后续状态判断。
- 复检流程管理。
- 档案审核和运维审核。
- 登录失败限制与敏感操作密码复核。
- 操作日志记录和审计查询。

### 3.3 Database

数据库负责保存系统结构化业务数据。

建议存储内容：

- 用户、角色、权限。
- 设备基础信息。
- 设备二维码标识和校验信息。
- 设备状态核验报告。
- 档案添加、删除和修改申请。
- 设备故障报修。
- 维修任务。
- 维修报告。
- 复检任务报告。
- 运维审核请求。
- 登录失败尝试和密码复核尝试。
- 操作日志。

### 3.4 后续预留：File Storage

当前版本未接入文件存储。后续附件能力落地后，文件存储负责保存图片、报告附件和其他非结构化文件。

设计要求：

- 业务表只保存附件元数据和访问引用，不直接保存大文件内容。
- 附件访问必须经过后端权限校验。
- 上传时必须限制文件类型、大小和数量。
- 后端必须对文件进行安全校验，不能只依赖扩展名。

### 3.5 后续预留：Push Service

当前版本通过刷新任务列表获取可接取任务。后续消息推送用于通知维修人员新故障、待处理任务和复检提醒。

初期可以先实现后端记录通知和移动端轮询，后续再接入系统推送能力。

推送内容不得包含敏感设备详情，应只包含摘要和业务标识，由移动端打开后再通过鉴权接口获取详情。

## 4. 后端工程结构

后端服务采用 Spring Boot 域优先结构。顶层目录先按业务域收拢，再在域内放置 API、服务、模型、仓储和基础设施代码；跨域公共能力放入 `shared`。

```text
rdvp-backend/
  src/
    main/java/com/rmf/rdvp/
      archive/     档案域：档案、二维码、档案申请相关模型和仓储
        api/       档案域 HTTP 接口和请求响应模型
      operations/  运维域：核验、报修、维修、复检和运维审核申请
        api/       运维域 HTTP 接口和请求响应模型
      review/      审核域占位：后续可承接独立审核编排能力
      log/         日志域：日志条目、日志查询和日志中心接口
        api/       日志域 HTTP 接口和请求响应模型
      home/        首页域：首页数据看板聚合
        api/       首页 HTTP 接口和响应模型
      user/        用户域：登录、会话、角色、权限和用户中心后续能力
        api/       用户域 HTTP 接口和请求响应模型
      shared/      跨域公共能力：API 响应、错误、配置、安全过滤器和系统接口
    main/resources/db/migration/
      Flyway 数据库迁移
```

`rdvp-backend` 是 RDVP 唯一后端工程。后续新增附件、通知和离线同步能力时，应优先判断它属于哪个业务域；只有确实跨域共享的能力才进入 `shared`。

结构规则：

- 域内 `api` 包只负责协议适配、参数接收和响应输出。
- 业务服务负责编排用例、权限校验和事务边界。
- 仓储实现负责数据库访问，SQL 必须使用当前域化物理表名。
- `shared/security` 只放安全过滤器、鉴权入口和跨域安全辅助；具体用户、角色、权限模型归属 `user`。
- `shared/api` 只放统一响应、异常处理和请求 ID 等协议公共件。
- 禁止恢复旧的顶层 `api`、`identity`、`security`、`config`、`dashboard`、`audit`、`domain` 技术层目录。

## 5. 移动端工程结构

HarmonyOS App 同样采用域优先结构。每个业务域内按同级语义放置 `pages`、`components`、`models`、`services`、`stores` 等目录；跨域通用 UI、主题、网络、安全和导航能力放入 `shared`。

```text
entry/src/main/ets/
  archive/      档案中心
    pages/
    models/
    services/
    stores/
  operations/   运维中心
    pages/
    components/
    models/
    services/
  review/       审核中心
    pages/
    models/
    services/
  log/          日志中心
    pages/
    models/
    services/
  home/         首页
    pages/
    models/
    services/
    stores/
  user/         用户中心、登录页和会话
    pages/
    models/
    services/
    stores/
  shared/       跨域通用组件、主题、网络、导航、安全、工具和公共状态
```

移动端实现规则：

- 页面不直接拼接复杂业务规则。
- API 调用放在对应业务域的 `services/`，跨域通用网络能力放在 `shared/services/`。
- 业务状态枚举放在对应业务域的 `models/`，跨域公共模型放在 `shared/models/`。
- 网络异常、权限不足和提交失败必须有明确用户提示。
- 登录界面命名为 `LoginPage`；首页命名为 `HomePage`，用户相关入口统一使用“用户中心”语义。
- 禁止恢复旧的顶层 `pages`、`components`、`models`、`services`、`stores`、`utils`、`styles` 技术层目录。
- 后续离线同步能力落地后，离线待同步内容与正式提交数据必须有明确状态区分。

## 6. 核心业务流向

### 6.1 档案查询

```text
进入档案查询
-> 选择设备编号查询或二维码查询
-> 移动端提交设备编号或二维码内容
-> 后端校验设备编号或二维码防伪信息
-> 后端返回档案和状态信息
-> 移动端进入档案详情
```

关键约束：

- 移动端不能直接信任二维码内容。
- 二维码防伪算法和密钥只能由后端掌控。
- 防伪校验失败必须记录操作日志；后续独立安全事件表落地后同步写入安全事件。
- 档案详情是档案添加、删除和修改申请的前置入口。

### 6.2 档案申请

```text
用户在档案详情中选择修改档案
-> 移动端预填当前档案
-> 用户修改字段并填写原因
-> 后端生成申请
-> 后端锁定该设备的档案申请入口
-> 管理员审核
-> 审核通过后更新设备主数据
-> 审核结束后设置 6 小时档案申请冻结期
-> 写入操作日志
```

关键约束：

- 设备主数据不能由普通用户直接修改。
- 必须保存修改前和修改后内容。
- 审核驳回必须保存驳回原因。
- 同一设备不能同时存在多个待审核档案申请。
- 6 小时档案冻结期必须由后端校验，冻结期从审核完成时间开始计算，移动端禁用入口只作为用户体验控制。

### 6.3 故障接取

```text
设备故障报修创建
-> 后端根据进行中任务数判定维修人员负载
-> 后端筛选符合负载与范围规则的维修人员
-> 维修人员刷新可接取任务列表
-> 维修人员主动接取
-> 后端进行负载校验和并发控制
-> 接取成功后生成维修任务
```

关键约束：

- 接取必须由后端保证同一故障只能被一个有效任务占用。
- 后续推送能力只作为提醒，不代表强制派单。
- 维修人员负载状态由系统根据进行中的维修任务数判定，移动端只展示判定结果。
- 忙碌状态不可刷新任务池或接取新任务，低负载状态只能在受限范围内接取任务。

### 6.4 维修与复检

```text
维修人员提交维修报告
-> 后端保存维修报告
-> 后端根据故障等级判断是否需要复检
-> 一般故障进入待关闭或已关闭
-> 重大故障进入待复检
-> 复检通过后关闭
```

关键约束：

- 是否复检由后端规则判断，不能只由移动端传参决定。
- 重大故障未复检通过前，设备不能恢复为正常状态。
- 复检不通过时，故障应重新进入维修处理流程。

### 6.5 后续预留：离线内容同步

当前版本未开放离线同步接口，以下流程仅作为后续增强设计。

```text
用户离线填写
-> 移动端保存至本地同步队列
-> 网络恢复后提交后端
-> 后端校验权限和业务状态
-> 同步成功后更新本地状态
```

关键约束：

- 本地待同步内容不等于后端正式提交。
- 同步时必须处理业务状态已变化的冲突。
- 涉及敏感信息的离线内容应考虑本地加密。

## 7. 状态和一致性原则

- 设备、故障、维修任务、复检任务报告的正式状态以后端数据库为准。
- 移动端只缓存展示数据和必要页面态；后续离线同步能力落地后，待同步内容必须与正式提交数据区分。
- 关键状态流转必须通过后端受控接口完成。
- 后端需要校验状态流转是否合法。
- 并发敏感操作必须由数据库事务或等价机制保证一致性。

并发敏感操作包括：

- 同一故障被多个维修人员同时接取。
- 同一设备存在多个待审核档案申请。
- 维修报告提交时故障状态已变化。
- 复检提交时维修任务已被取消或重开。

## 8. 安全边界

### 8.1 认证边界

- 所有业务接口必须要求登录。
- 访问凭证必须有过期时间。
- 退出登录后应清理移动端本地会话状态。

### 8.2 授权边界

- 后端必须根据角色和权限判断用户是否能执行操作。
- 移动端控制功能入口不等于安全授权。
- 操作日志必须记录执行人、执行时间、操作类型和业务对象。

### 8.3 二维码安全边界

- 防伪密钥不得放入移动端。
- 二维码签名必须由后端生成或校验。
- 二维码校验失败、重复异常扫描等行为应进入安全日志。

### 8.4 文件安全边界

- 后续文件上传必须鉴权。
- 后续文件下载必须鉴权。
- 后续文件类型、大小和数量必须受限。
- 后续文件存储路径不得由客户端直接指定。

## 9. 部署形态

第一阶段部署形态：

```text
HarmonyOS App
-> HTTPS
-> Backend Service
-> Database
```

后续可扩展：

```text
Web Admin Console
-> Backend Service
-> Database
-> File Storage
-> Push Service
-> Audit / Log Service
```

## 10. 技术决策待定

以下技术选型后续需要单独确认：

- 附件和通知 API 的 Spring Boot 实现顺序。
- 文件存储方式。
- 推送服务实现方式。
- 二维码密钥轮换和密钥管理方式。
- 离线待同步内容本地存储和加密方案。
- 是否需要 Web 管理后台。
- 是否需要多组织或多租户能力。
