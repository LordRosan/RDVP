## 1. 架构目标

RDVP 的架构设计目标如下：

- 支持 HarmonyOS 移动端完成现场设备查询、核验、故障上报、维修接取、维修报告和复检等业务。
- 支持后端统一管理设备数据、业务流程、权限控制、附件、推送和审计日志。
- 保证关键业务状态以后端为准，移动端不能绕过后端直接改变设备真实状态。
- 支持离线填写草稿，但正式业务数据必须在后端校验通过后才生效。
- 支持后续扩展 Web 管理后台、统计报表、多组织管理和外部系统集成。

## 3. 工程边界

### 3.1 HarmonyOS App

移动端应用负责用户交互和现场数据采集，不能承担最终业务判定职责。

主要职责：

- 展示用户可访问的功能入口。
- 采集设备编号、二维码、核验内容、故障内容、维修内容和附件。
- 管理本地草稿和待同步数据。
- 提醒用户当前网络状态和同步状态。
- 调用后端接口完成业务提交和查询。

移动端不得承担以下职责：

- 不得在本地直接判定二维码真实可信。
- 不得在本地直接改变设备最终状态。
- 不得在本地绕过权限控制。
- 不得保存明文密码、长期密钥或生产环境敏感配置。

### 3.2 Backend Service

后端服务是业务事实来源，负责所有关键业务规则和状态流转。

主要职责：

- 登录认证和访问凭证签发。
- 用户、角色和权限校验。
- 设备基础信息维护。
- 设备信息变更申请和审核。
- 二维码防伪校验。
- 故障报告创建和状态流转。
- 附近维修人员筛选和故障推荐。
- 维修任务接取并发控制。
- 维修报告保存和后续状态判断。
- 复检流程管理。
- 附件上传、访问控制和元数据管理。
- 操作日志记录和审计查询。

### 3.3 Database

数据库负责保存系统结构化业务数据。

建议存储内容：

- 用户、角色、权限。
- 设备基础信息。
- 设备二维码标识和校验信息。
- 设备状态核验记录。
- 设备信息变更申请。
- 故障报告。
- 维修任务。
- 维修报告。
- 复检记录。
- 附件元数据。
- 操作日志。

### 3.4 File Storage

文件存储负责保存图片、报告附件和其他非结构化文件。

设计要求：

- 业务表只保存附件元数据和访问引用，不直接保存大文件内容。
- 附件访问必须经过后端权限校验。
- 上传时必须限制文件类型、大小和数量。
- 后端必须对文件进行安全校验，不能只依赖扩展名。

### 3.5 Push Service

消息推送用于通知维修人员新故障、待处理任务和复检提醒。

初期可以先实现后端记录通知和移动端轮询，后续再接入系统推送能力。

推送内容不得包含敏感设备详情，应只包含摘要和业务标识，由移动端打开后再通过鉴权接口获取详情。

## 4. 后端分层建议

后端服务建议采用清晰的分层结构：

```text
backend-service/
  src/
    api/          接口入口和请求响应模型
    application/ 业务用例编排
    domain/      领域模型、状态规则和业务约束
    infrastructure/
                 数据库、文件存储、推送、外部服务适配
    security/    认证、授权、凭证、密码和安全过滤
    audit/       操作日志和审计事件
```

当前 `backend-service` 的第一阶段实现使用内存型基础设施适配器，用于验证 API 边界、领域状态流转和本地开发流程。后续接入数据库时应保持 `application` 与 `domain` 层规则稳定，将持久化实现替换到 `infrastructure` 层。

分层规则：

- `api` 层只负责协议适配、参数接收和响应输出。
- `application` 层负责编排业务用例和事务边界。
- `domain` 层表达核心业务规则，例如故障状态流转、复检判定、接取规则。
- `infrastructure` 层处理数据库、文件、推送等外部技术细节。
- `security` 层集中处理认证和授权。
- `audit` 层集中记录关键业务动作。

## 5. 移动端分层建议

HarmonyOS App 建议按页面、状态、服务和模型拆分：

```text
entry/src/main/ets/
  pages/       页面入口
  components/ 复用组件
  models/     前端数据模型
  services/   API 调用、认证、附件、同步等服务
  stores/     页面状态和会话状态
  utils/      通用工具
```

移动端实现规则：

- 页面不直接拼接复杂业务规则。
- API 调用集中放在 `services/`。
- 业务状态枚举集中定义，避免页面中散落字符串。
- 离线草稿与正式提交数据必须有明确状态区分。
- 网络异常、权限不足、同步失败必须有明确用户提示。

## 6. 核心业务流向

### 6.1 设备档案查询

```text
进入设备档案查询
-> 选择设备编号查询或二维码查询
-> 移动端提交设备编号或二维码内容
-> 后端校验设备编号或二维码防伪信息
-> 后端返回设备档案和状态信息
-> 移动端进入设备档案详情
```

关键约束：

- 移动端不能直接信任二维码内容。
- 二维码防伪算法和密钥只能由后端掌控。
- 防伪校验失败必须记录安全事件。
- 设备档案详情是设备档案变更的前置入口。

### 6.2 设备信息变更

```text
用户在设备档案详情中选择修改设备档案
-> 移动端预填当前设备档案
-> 用户修改字段并填写原因
-> 后端生成变更申请
-> 后端锁定该设备的档案变更入口
-> 管理员审核
-> 审核通过后更新设备主数据
-> 设置 12 小时变更冻结期
-> 写入操作日志
```

关键约束：

- 设备主数据不能由普通用户直接修改。
- 必须保存修改前和修改后内容。
- 审核驳回必须保存驳回原因。
- 同一设备不能同时存在多个待审核变更申请。
- 12 小时变更冻结期必须由后端校验，移动端禁用入口只作为用户体验控制。

### 6.3 故障接取

```text
故障报告创建
-> 后端筛选附近空闲维修人员
-> 发送故障提醒
-> 维修人员主动接取
-> 后端进行并发控制
-> 接取成功后生成维修任务
```

关键约束：

- 接取必须由后端保证同一故障只能被一个有效任务占用。
- 推送只是提醒，不代表强制派单。
- 维修人员空闲状态需要可查询、可更新、可审计。

### 6.4 维修与复检

```text
维修人员提交维修报告
-> 后端保存维修报告
-> 后端根据故障等级判断是否需要复检
-> 一般故障进入待关闭或已关闭
-> 重大故障进入待复检
-> 复检通过后关闭
```

关键约束：

- 是否复检由后端规则判断，不能只由移动端传参决定。
- 重大故障未复检通过前，设备不能恢复为正常状态。
- 复检不通过时，故障应重新进入维修处理流程。

### 6.5 离线草稿同步

```text
用户离线填写
-> 移动端保存本地草稿
-> 网络恢复后提交后端
-> 后端校验权限和业务状态
-> 同步成功后更新本地状态
```

关键约束：

- 离线草稿不等于正式提交。
- 同步时必须处理业务状态已变化的冲突。
- 涉及敏感信息的离线草稿应考虑本地加密。

## 7. 状态和一致性原则

- 设备、故障、维修任务、复检记录的正式状态以后端数据库为准。
- 移动端只缓存展示数据和待同步草稿。
- 关键状态流转必须通过后端受控接口完成。
- 后端需要校验状态流转是否合法。
- 并发敏感操作必须由数据库事务或等价机制保证一致性。

并发敏感操作包括：

- 同一故障被多个维修人员同时接取。
- 同一设备存在多个待审核变更申请。
- 维修报告提交时故障状态已变化。
- 复检提交时维修任务已被取消或重开。

## 8. 安全边界

### 8.1 认证边界

- 所有业务接口必须要求登录。
- 访问凭证必须有过期时间。
- 退出登录后应清理移动端本地会话状态。

### 8.2 授权边界

- 后端必须根据角色和权限判断用户是否能执行操作。
- 移动端控制功能入口不等于安全授权。
- 操作日志必须记录执行人、执行时间、操作类型和业务对象。

### 8.3 二维码安全边界

- 防伪密钥不得放入移动端。
- 二维码签名必须由后端生成或校验。
- 二维码校验失败、重复异常扫描等行为应进入安全日志。

### 8.4 文件安全边界

- 文件上传必须鉴权。
- 文件下载必须鉴权。
- 文件类型、大小和数量必须受限。
- 文件存储路径不得由客户端直接指定。

## 9. 部署形态

第一阶段部署形态：

```text
HarmonyOS App
-> HTTPS
-> Backend Service
-> Database
-> File Storage
```

后续可扩展：

```text
Web Admin Console
-> Backend Service
-> Database
-> File Storage
-> Push Service
-> Audit / Log Service
```

## 10. 技术决策待定

以下技术选型后续需要单独确认：

- 后端语言和框架。
- 数据库类型。
- 文件存储方式。
- 推送服务实现方式。
- 二维码签名算法和密钥管理方式。
- 离线草稿本地存储和加密方案。
- 是否需要 Web 管理后台。
- 是否需要多组织或多租户能力。
